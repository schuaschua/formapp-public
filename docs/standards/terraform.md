# Terraform Standards

Applies to everything under `infra/`. The architecture spine is binding: where this file and the spine disagree, the spine wins. Azure resource naming, tagging and region rules are in [azure.md](azure.md) and are not repeated here.

Sources: spine = `_bmad-output/planning-artifacts/architecture/architecture-formapp-2026-09-25/ARCHITECTURE-SPINE.md`; TFBP = [terraform-best-practices.com](https://www.terraform-best-practices.com/); AVM = [Azure Verified Modules](https://azure.github.io/Azure-Verified-Modules/).

## Directory tree

```text
infra/
  bootstrap/
    state-backend.sh      # az CLI, idempotent: RG + storage account + container for state. Run once, outside Terraform.
    README.md             # how to run it; the manual pgaadauth_create_principal step (api and pipeline principals)
  modules/                # project modules that compose AVM modules; no provider or backend blocks
    <name>/
      main.tf
      variables.tf
      outputs.tf
      versions.tf         # required_providers only (no provider config)
      README.md           # generated by terraform-docs
  demo/                   # one folder per environment; environments share nothing
    foundation/           # stack 1
      main.tf
      variables.tf
      outputs.tf          # values the agent stack needs (FQDN, Foundry endpoint, ...)
      versions.tf         # required_version, required_providers, backend "azurerm"
      providers.tf        # provider "azurerm" / "azapi" configuration
      locals.tf           # optional: derived names, common tags
      terraform.tfvars    # environment values; no secrets
      .terraform.lock.hcl # committed
    agent/                # stack 2: same file set, plus data.tf for terraform_remote_state
```

## Apply order (per environment)

1. Once per subscription: run `infra/bootstrap/state-backend.sh`. It creates the state storage, `rg-sample-demo-sea`, the pipeline's deployment identity with its role assignments, and the resource provider registrations (azure.md rule 31).
2. `infra/demo/foundation`: `terraform plan -out=tfplan`, human approves, `terraform apply tfplan`.
3. Once, after the first foundation apply: the manual `pgaadauth_create_principal` step in `infra/bootstrap/README.md`. It creates database principals for the `api` identity and the pipeline identity, creates the migration role, and grants that role only to the pipeline identity.
4. Build and push images with `az acr build` (outside Terraform).
5. Run database migrations (`alembic upgrade head`) from the GitHub Actions runner (outside Terraform; rule 36).
6. `infra/demo/agent`: plan, human approves, apply the saved plan.
7. Post-deploy smoke check.

Destroy in reverse: agent, then foundation, only through the pipeline's Destroy demo workflow (started by hand on `main`, with a typed confirmation), never locally.

## Rules

### Layout & stacks

1. Keep the medium layout: shared modules in `infra/modules/`, one root folder per environment under `infra/<env>/`. (spine AD-11; [TFBP: medium-terraform example](https://github.com/antonbabenko/terraform-best-practices/tree/master/examples/medium-terraform))
2. Each environment has exactly two stacks, `foundation` and `agent`, with the resources AD-11 assigns to each. Moving a resource between stacks means amending AD-11. `foundation` owns the Container App with `lifecycle.ignore_changes` on its image and agent environment variables; `agent` sets those with `azapi_resource_action` (`PATCH`). (spine AD-11)
3. Environments share nothing: no cross-environment remote-state reads, no shared state, no shared tfvars. (spine Deferred; [TFBP: medium-terraform example](https://github.com/antonbabenko/terraform-best-practices/tree/master/examples/medium-terraform))
4. Every root contains the standard file set shown above; modules contain `main.tf`, `variables.tf`, `outputs.tf`, `versions.tf` and no `terraform.tfvars`. ([TFBP: Code structure](https://www.terraform-best-practices.com/code-structure))

### State

5. Store all state in the `azurerm` backend created by the bootstrap script, one key per stack: `<env>/<stack>.tfstate`. Never commit state or keep it local. (spine AD-11; [TFBP: Code structure](https://www.terraform-best-practices.com/code-structure))
6. Configure the backend with `use_azuread_auth = true`; no storage account keys or SAS tokens.
7. Stacks exchange values only through `data "terraform_remote_state"` reading the other stack's outputs. `agent` reads `foundation`; `foundation` never reads `agent`. (spine AD-11; [TFBP: Key concepts](https://www.terraform-best-practices.com/key-concepts))
8. Expose only what the consumer stack needs as `foundation` outputs; the agent stack must not look foundation resources up by name with data sources.

### Providers & versions

9. Use the latest stable (non-preview) versions of Terraform, the providers and each AVM module at the time the code is written, and pin them exactly in every root so builds are reproducible. Resource API versions are stable too. Container Apps `authConfigs` uses GA `2026-07-01` with `schema_validation_enabled = false`, because azapi 2.12.0 doesn't know that version yet (owner-approved; security.md section 9). Upgrades are deliberate: bump the pin, run `plan`, and update the spine Stack table. The spine Stack table lists the versions current at planning time. (spine Stack)
10. Commit `.terraform.lock.hcl` for every root.
11. Configure providers only in a root's `providers.tf`; modules declare `required_providers` and never contain `provider` blocks. ([TFBP: Key concepts](https://www.terraform-best-practices.com/key-concepts))
12. Use `azurerm` for hand-written resources; use `azapi` only where `azurerm` does not model the resource (Container Apps `authConfigs`, the Foundry hosted agent via `azapi_data_plane_resource`). Add a comment naming the missing `azurerm` resource. One exception: the `agent` stack patches the Container App image and agent environment variables with `azapi_resource_action` (`PATCH`), because two stacks can't both own the resource. (spine AD-11)

### Modules (AVM first)

13. Use an Azure Verified Module whenever one fits: `source = "Azure/avm-res-<service>-<resource>/azurerm"` (or `avm-ptn-*` for patterns). Check the [AVM Terraform resource module index](https://azure.github.io/Azure-Verified-Modules/indexes/terraform/tf-resource-modules/) first. (spine AD-11; [AVM: module specs](https://azure.github.io/Azure-Verified-Modules/specs/tf/))
14. Pin every AVM module to an exact `version = "x.y.z"`, never a range. (spine AD-11)
15. Only use AVM modules marked Available; for Proposed/missing modules (e.g. consumption budget) hand-write the resource per rule 12.
16. Set `enable_telemetry = true` explicitly in every AVM module call (telemetry kept on). ([AVM: solution development](https://azure.github.io/Azure-Verified-Modules/usage/solution-development/terraform/))
17. Compose AVM modules in `infra/modules/<name>/`; roots call `infra/modules/*` or AVM modules, never other roots.

### Naming & style

18. Use lower `snake_case` for all Terraform identifiers (resources, data sources, variables, outputs, locals); dashes only in Azure resource name values (see [azure.md](azure.md)). ([TFBP: Naming](https://www.terraform-best-practices.com/naming); [AVM: TFNFR4](https://azure.github.io/Azure-Verified-Modules/specs/tf/res/))
19. Do not repeat the resource type in the name (`azurerm_container_app.api`, not `.api_container_app`); use `this` only when a module has one resource of that type. ([TFBP: Naming](https://www.terraform-best-practices.com/naming))
20. Argument order: `count`/`for_each` first, then arguments, `tags` last, then `depends_on`, then `lifecycle`. ([TFBP: Naming](https://www.terraform-best-practices.com/naming))
21. Code must pass `terraform fmt -check -recursive` and `terraform validate`. Comments use `#` only. ([TFBP: Code styling](https://www.terraform-best-practices.com/code-styling))

### Variables & outputs

22. Every variable and output has a `description`; variable keys ordered `description`, `type`, `default`, `validation`; plural names for lists/maps; no double negatives. ([TFBP: Naming](https://www.terraform-best-practices.com/naming))
23. No hardcoded environment values in `main.tf`; they come from `terraform.tfvars` or `locals.tf`. ([TFBP: Code structure](https://www.terraform-best-practices.com/code-structure))

### Secrets & identity

24. No secrets in `.tf`, `.tfvars`, outputs or commits. Generate secrets (e.g. the turn-token signing key) with `random_password` and write them directly to Container Apps secrets; mark related outputs `sensitive = true`. (spine AD-4, Config)
25. Services authenticate with managed identity and role assignments declared in Terraform; no passwords or keys for PostgreSQL, ACR or Foundry. (spine AD-5, AD-10, Auth)

### Workflow (plan/apply/approval)

26. Always `terraform plan -out=tfplan`, have a human review and approve that plan (the owner reviews the plan pasted on the pull request into `main` from `scripts/check.sh --plan`, then starts the deploy run, which plans again, rule 33), then `terraform apply tfplan`. Never `apply -auto-approve` and never apply without a saved, approved plan. (spine AD-11)
27. Apply stacks strictly in the order above; a failed step stops the sequence. (spine AD-11)

### Forbidden

28. No `local-exec`, `remote-exec` or `file` provisioners, and no `null_resource`/`terraform_data` used to run scripts. (spine AD-11)
29. No portal or CLI changes to Terraform-managed resources; the only out-of-band steps are the state-backend bootstrap, `az acr build`, the pipeline's migration step (rule 36), and the `pgaadauth_create_principal` step. (spine AD-11)
30. No `terraform import`, `state mv/rm` or `-target` without a note in the PR explaining why.

### CI/CD (GitHub Actions)

31. All code lives in one GitHub repository; workflows are YAML in `.github/workflows/`. (spine AD-11)
32. Before every push, `scripts/check.sh` runs `terraform fmt -check` locally, and for an `infra/` change `scripts/check.sh --plan` runs `plan` for each stack; the plan summary goes in the pull request. GitHub Actions runs no pull-request checks (owner decision, 2026-09-27). `validate` and the mock-provider tests run only for the affected roots and modules: each changed `infra/modules/<m>` and each changed `infra/demo/<stack>`, plus every `infra/demo/*` root when any module changed (roots use the modules), or every root and module when `.tflint.hcl` or `scripts/check.sh` changed. The `storage-account`, `resource-group`, `postgresql-flexible-server`, `log-analytics-workspace`, `container-registry` and `container-apps-environment` modules and the `foundation` root are skipped (POC only); a plan still parses and validates their configuration. (spine AD-11)
33. Merges to `main` never apply. The owner starts the deploy workflow by hand (`workflow_dispatch`) on `main`, in the GitHub Environment `demo` (deployment branch policy: `main` only); that manual run is the human approval in rule 26. `workflow_dispatch` is its only trigger; it deploys only the current `main` HEAD, one run at a time (queued, never cancelled), and fails on any destroy or replace of PostgreSQL, the Container Apps environment or Foundry. It runs in the order `foundation`, `az acr build`, database migrations, `agent`, post-deploy smoke check. Destroying uses the Destroy demo workflow the same way (manual, `main` HEAD only, same queue, never cancelled): a run with mode `plan` shows the destroy plans for review, and a second run with mode `destroy` and the typed confirmation `rg-sample-demo-sea` applies them; the destroy/replace guard does not apply there. (spine AD-11)
34. Workflows log in to Azure with OIDC workload identity federation. No stored Azure secrets; the tenant, subscription and client IDs are non-secret repository variables. (spine AD-11)
35. State stays in the Azure Storage backend (rule 5) and never goes into git or workflow artifacts. `.gitignore` covers `*.tfstate*`, `.terraform/` and any `*.tfvars` that holds secrets. (spine AD-11)
36. The migration step runs `alembic upgrade head` on the runner, signed in to PostgreSQL with the pipeline's OIDC identity through Entra auth (no password). It reaches PostgreSQL only through the allow-all firewall rule (`postgresql_allow_public_access`): development environments may have their firewall open to all addresses for a temporary period (owner policy, 2026-09-27). There is no per-run firewall rule; if `postgresql_allow_public_access` is ever set to false, the migration step can't connect, and the per-run firewall steps removed in FORM-7 would have to be restored. A failed migration stops the deploy, so the `agent` stack runs only after a successful migration. (spine AD-10, AD-11, AD-17)

## Not applied in the POC

| Item | Revisit when |
| --- | --- |
| Additional environments | A second environment is needed: add `infra/<env>/foundation` and `infra/<env>/agent`, same subscription (spine Deferred). |
| Terragrunt or other orchestration | More than ~3 environments or stacks make root duplication painful. |
| pre-commit hooks, terraform-docs automation, tflint/checkov | The CI/CD pipeline (rules 31-35) is working. |
| Key Vault, private networking | After the POC (spine Deferred). |
| State locking/lease tuning, state storage redundancy beyond defaults | Real data or more than one operator. |
| `validate` and tests in CI for the `foundation` root and the six modules in rule 32 (its tests stay in `infra/demo/foundation/tests/` and can be run locally), and the storage-account module's own tests (removed 2026-09-27 to speed up CI) | A UAT or production environment is added (restore the full CI suite). |
